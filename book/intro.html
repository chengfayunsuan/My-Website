PREFACE 这本书想干什么

它不是一本教材，是一条因果链。每一环都必须由上一环推出来。

一个场景

你双击桌面上的图标，窗口弹出来。这件事你做过几万次，几乎没出过错。

但如果我问：那个图标指向的文件，系统是怎么找到的？找到之后，是谁判定它可以运行？ 运行的时候，它向系统要了什么？它画在屏幕上的那些像素，又是经由哪条路径送到显示器上的？

大多数人说不出。不是笨，是从来没人从底下往上讲过一遍。

一句话

这本书只做一件事：把「从一枚晶体管到一家公司」这条链，一环一环接起来，中间不留断口。

不留断口，是个很高的要求。它意味着任何一处你读不下去，都不是因为「这里需要你先懂点别的」—— 需要先懂的东西，一定在前面已经讲过了。

为什么顺序不能打乱

市面上大部分计算机入门书是「按主题分块」的：这一章讲硬件，那一章讲网络，再一章讲编程。 块与块之间，靠读者自己脑补。

这本书不这么干，因为它只有一条规则：

任何一节里出现的名词，都必须在它之前被解释过。

举个具体的例子。很多人学 Web 是从「API」开始的：调一个接口，拿到一段 JSON，渲染到页面上。 看起来学会了。但如果问他：这个请求在网络上是什么形状？它怎么找到那台服务器？ 服务器凭什么相信「你是你」？JSON 里那个时间戳为什么是 1970 年以来的秒数？

答不上来。不是 API 没学好，是 API 底下压着六层东西没铺。

所以这里的顺序是硬的：电 → 逻辑门 → CPU → 操作系统 → 文件 → 网络 → 协议 → 网站 → 钱 → 公司。 你不能先看 HTTP 再看 TCP，也不能先看 Node.js 再回头补端口。

注意第 7 部和第 8 部的位置。很多人会觉得「钱和公司」跟计算机没关系，应该砍掉。 恰恰相反——你写的程序要收钱，就得办营业执照、开对公账户、签支付通道、开发票、做备案。 这些不是技术的「外围」，它们就是技术落地时必须穿过的那层膜。跳过它们，你会以为「上线」等于「部署成功」。

五条约定

每节自包含
开头会用一两百字把必需的前置重新交代一遍。单独抽一节给别人看，也不会断头。
图是独立文件
每张图都是一个单独的 SVG，不是截屏也不是位图。放大不糊，颜色跟着深色底走。
「深入」块
正文讲主干，标着「深入」的块讲这一节最硬的那点细节。第一遍可以跳过，第二遍回来吃。
每节结尾有自测
不是选择题，是「你能不能用一句话解释给外行听」。答不上来，说明这节还得再读一遍。
字数不设配额
讲得完的八千字就收尾，讲不完的两万字也不够。字数服从「讲清楚」，不服从指标。

我不写什么

一份诚实清单，省得你抱着错误的期待读下去：

  • 不写算法竞赛。那是另一门手艺，需要大量刷题，跟「理解计算机怎么运转」是两条路。
  • 不写框架源码解析。框架三年换一代，写进去就过期。这里只讲框架在解决什么问题。
  • 不写数学证明。需要证明的地方（比如浮点误差、哈希碰撞）我会给结论和直觉，把严格推导指到该去的地方。
  • 不写「最佳实践」清单。脱离场景的最佳实践都是口号。这里给的是「什么情况下该选哪个，代价是什么」。

三种读法

全书近四百个小节。全部读完是个以年计的事，所以给了三条路：

  • 顺序读。从 0.1.1 一路到尾。唯一不需要补前置的方式，也是最慢的。
  • 速通读。只读标 ★ 的那些节。跳过的部分在正文里都有指路，不会断链。
  • 缺口读。先翻第 13 部的自查题，答不上的，按编号回来补那一节。

最后

这本书有个隐含的野心，比「讲完所有知识」小，但更有用：

读完它，你看到一个陌生的软件、一条陌生的报错、一张陌生的账单， 都能大致判断出「它在哪一层」。

知识会过期，分层不会。会分层的人，遇到没见过的东西也知道从哪儿开始查； 不会分层的人，只能背下所有见过的答案。

那我们开始。往下翻，第一件事是找一把螺丝刀。
